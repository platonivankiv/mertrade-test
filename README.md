# Тестовое задание МЭР Трейд — инженер по интеграциям

## Состав

| Папка | Задание |
|---|---|
| `04/` | Разбор обращений сотрудников по логам (обязательное) |
| `03/` | B2B-сайт: почему у клиента «не та» цена |
| `06/` | Своё улучшение |

Почему выбрал 03: я frontend-разработчик, и задачи вида «пользователь видит не те данные» — моя ежедневная работа: разобраться, где ошибка — в коде, в данных с бэкенда или в кеше. В 03 ровно такая задача: пять обращений, у каждого своя причина (код, данные, кеш или ожидания, расходящиеся с правилами), и её нужно доказать, а не угадать. Кешированием и согласованностью данных я много занимался на фронтенде (TanStack Query, Apollo). В MBOptions — системе мониторинга торговых сервисов с данными двух брокеров, EXANTE и Interactive Brokers, — я держал позиции, прибыль и статусы счетов актуальными, опрашивая сервер раз в 10–60 с, поэтому случай с устаревшим кешем мне особенно близок. 01 и 05 не взял: в них больше чистого бэкенда, а 03 — именно разбор, откуда взялись неправильные данные.

## Как запустить

Требуется PHP 8.1+.

04 — скрипты для перепроверки цифр в разборе (из корня репозитория):

```bash
bash 04/scripts/inc2_count.sh   # inc2: 503 по клиентам, оформления заказа в эпизодах, бот и cron
bash 04/scripts/inc3_check.sh   # inc3: на каком задании встал обмен и как росла очередь
```

03:

```bash
cd 03
php run.php K-001 B-101
php run.php K-003 B-105                 # ожидаемо завершается ошибкой «Нет цены DEALER для B-105»
php tests/scenarios.php                 # сценарии по 5 обращениям, без зависимостей
git checkout var/cache.json             # run.php перезаписывает кеш; так он возвращается к исходному
```

Исходный кеш сохранён в `03/var/cache.orig.json`, на него опирается тест «4a». Тесты пишут кеш во временный файл и `var/cache.json` не трогают.

06 — прототип мониторинга обменов (из корня репозитория):

```bash
php 06/prototype/monitor.php --now="2026-10-22 08:20"                              # данные со сбоем: 4 алерта, код 1
php 06/prototype/monitor.php --data=06/prototype/data/ok --now="2026-10-22 08:20"  # без сбоев: «Всё в порядке», код 0
```

## Принятые решения

- 04: по каждому обращению сначала краткий разбор на 5–10 строк, как в условии, под ним — «Подробности» с доказательствами. Короткий формат удобно читать, а доказательства не потеряны.
- 03: при отсутствии цены нужного типа `PriceResolver::basePrice()` бросает исключение вместо подстановки розничной цены. Розничная цена для дилера — это переплата и претензии клиента; ближайший тип цен (например, оптовая 2) — это продажа по цене, которую никто не утверждал. Плата за решение: пока цену не заведут в 1С, клиент не может купить товар. Смягчить это нужно в месте вызова, а не в `PriceResolver`: показать «цена по запросу» и не давать оформить заказ. Поэтому `php run.php K-003 B-105` теперь завершается ошибкой «Нет цены DEALER для B-105», так и задумано.
- 03: ключ кеша без типа цен — недостаток кода, но кеш в `PriceResolver.php` не меняю (правка «не больше, чем нужно»); случай №4 закрывается сбросом кеша, профилактика описана в `03/03-answers.md`.
- 03: тесты — `03/tests/scenarios.php` без PHPUnit, кеш пишется во временный файл, `var/cache.json` не трогается.
- 03: акция действует до конца дня `valid_to` по времени Минска (`run.php:32`).
- 06: проблема — «обмен с 1С встаёт, а узнают от бухгалтерии» (примеры — inc3 и inc4 из 04). Решение — внешний мониторинг, который только читает данные обмена; правки самого обмена — второй этап, после согласования.
- 06: прототип читает выдуманные JSON/CSV вместо БД и лога и печатает алерты в консоль; отправки в Telegram и защиты от повторных алертов нет — описано в `06/prototype/README.md`.
- 06: «текущее время» передаётся параметром `--now`, чтобы вывод на выдуманных данных был воспроизводимым.

## Что не успел

- 04: выводы, помеченные «гипотеза», не проверены — нужны данные из разделов «Что ещё запросить» в `04/04-incidents.md`. В inc2 не объяснён эпизод 09:15.
- 03: профилактика кеша только описана в `03/03-answers.md`, в коде не сделана (правка «не больше, чем нужно»).
- 06: в прототипе нет чтения из БД и лога, отправки в Telegram и защиты от повторных алертов.
