## 1. K-003 (дилер) видит на B-105 розничную цену

**Причина:** данные + код. В выгрузке цен из 1С для B-105 нет дилерской цены: `data/prices.csv:18-20` — только `RETAIL 4.90`, `OPT1 4.41`, `OPT2 4.17`. Старый `basePrice()` в таком случае без предупреждения брал розницу: `src/PriceResolver.php:54` (до правки) `?? $this->prices[$sku]['RETAIL']`. Скидка 4 % (акция «Октябрь» на хозтовары) применялась верно, неверна база.

**Как установлено:** `php run.php K-003 B-105` → `базовая цена: 4.90` (= RETAIL); поиск `grep B-105 data/prices.csv` — строки DEALER нет. Почему цены нет в 1С (не заведена или не выгрузилась) — **гипотеза**, проверить в 1С тип цен «Дилерская» по B-105 и журнал обмена.

**Исправление в коде:** при отсутствии цены нужного типа `basePrice()` бросает `RuntimeException("Нет цены DEALER для B-105")` — товар не продаётся по чужой цене, ошибка видна сразу (тест «1»).

**Что сделать сейчас:** попросить ответственного за цены в 1С завести дилерскую цену на B-105 и выгрузить на сайт; если K-003 уже оформил заказ по 4.70 — пересчитать по дилерской цене после её появления (ориентир по соседним типам — ниже 4.17, но точную цифру даёт только 1С). Проверить после: `php run.php K-003 B-105` показывает дилерскую базу.

**Ответ менеджеру:** «Для этого товара в 1С не заведена дилерская цена, поэтому сайт показывал розничную. Пока цену не заведут, клиент не сможет заказать этот товар на сайте, при срочной необходимости оформите заказ вручную по согласованной цене; уже оформленный заказ пересчитаем».

## 2. K-001 получает на B-101 скидку 7 % по закончившейся акции «Сентябрь»

**Причина:** ошибка в коде. `src/PriceResolver.php:78-80` (до правки) сравнивал даты как строки `дд.мм.гггг`: `"22.10.2026" <= "30.09.2026"` → `true`, потому что сравнение посимвольное и сначала сравниваются дни (22 < 30). Акция R2 (`data/discount_rules.json:5`, до 30.09.2026) считалась действующей. Ошибка плавающая: зависит от числа месяца.

**Как установлено:** `php run.php K-001 B-101` → `скидка: 7.00%`; `php -r 'var_dump("22.10.2026" <= "30.09.2026");'` → `bool(true)`. Тесты «2» и «2b» (01.10) падали, «2a» (30.09 — последний день действует) проходил.

**Исправление в коде:** даты правила разбираются через `DateTimeImmutable::createFromFormat('!d.m.Y', …)` и сравниваются в формате `Y-m-d`; `valid_to` включительно, как в правиле (`TASK.md:12`).

**Что сделать сейчас:** выложить исправление и сбросить кеш цен (иначе старые цены со скидкой продержатся до суток). Проверить заказы с 01.10 по канцтоварам, где применилась скидка 7 %, — решение по ним (оставить клиентам или нет) за коммерческим отделом.

**Ответ менеджеру:** «Это была ошибка сайта: он неправильно сравнивал даты и продолжал применять сентябрьскую акцию. Ошибку исправили, теперь цена без скидки — 14,75».

## 3. K-002 получил на 12 шт. B-106 скидку 12 %

**Причина:** ошибка в коде. `src/PriceResolver.php:59,66,69` (до правки) складывал скидки: персональная 5 % (`data/clients.csv:3`) + объёмная 3 % (R1, от 10 шт.) + акция «Октябрь» 4 % (R3) = 12 %. По правилу скидки не суммируются, берётся одна максимальная (`TASK.md:11`, `data/discount_rules.json:2`).

**Как установлено:** `php run.php K-002 B-106 12` → `скидка: 12.00%`, сумма совпадает с 5 + 3 + 4; тест «3» падал. Тест «3b» (K-001, 12 шт., без персональной скидки) проверяет выбор между объёмной скидкой и акцией: было 3 + 4 = 7 %, стало 4 %.

**Исправление в коде:** `$percent = max($percent, $rule['percent'])` вместо `+=`. Теперь max(5, 3, 4) = 5 % → 3.69 × 0.95 = **3.51** (было 3.25).

**Что сделать сейчас:** выложить исправление, сбросить кеш. Найти заказы, где одновременно сработало больше одной скидки, — по ним клиенты получили лишнюю скидку; решение по уже оформленным — за коммерческим отделом.

**Ответ менеджеру:** «Вы правы, сайт ошибочно складывал все скидки вместо того, чтобы взять одну наибольшую. Исправили: для K-002 действует его персональная скидка 5 %, цена 3,51 за штуку».

## 4. K-004 переведён на оптовую 2, а на B-103 всё ещё 15,48

**Причина:** кеш. Ключ кеша без типа цен — недостаток кода, но по правилу «не больше, чем нужно» его не исправляю: профилактика описана ниже. В кеше есть запись `price:K-004:B-103:1` = 15.48, создана 22.10 в 09:05, живёт до 23.10 09:05 (`var/cache.orig.json:2-5`). Тип цен сменили в 10:30, но кеш живёт сутки (`src/PriceResolver.php:91`, TTL 86400), его ключ не зависит от типа цен, и при смене клиента он не сбрасывается — сайт отдаёт старую цену.

**Как установлено:** `php run.php K-004 B-103` → `базовая цена: 15.72` (уже OPT2, `data/prices.csv:12`), но `цена на сайте: 15.48` — не совпадает с расчётом, значит взята из кеша. Тесты «4a» (со старым кешем — 15.48) и «4b» (без кеша — 15.72). 15.48 = 16.65 (OPT1) × 0.93 — то есть цена посчитана ещё по оптовой 1 и с ошибочной сентябрьской скидкой (№2) — **гипотеза** по совпадению цифр.

**Что сделать сейчас:** **после** выкладки исправления №2 удалить из кеша ключи K-004 (или весь кеш цен). Порядок важен: если сбросить кеш на старом коде, сайт пересчитает 15.72 × 0.93 = 14.62 — снова неверно. Проверить после: `php run.php K-004 B-103` → 15.72.

**Ответ менеджеру:** «Сайт запоминает цены на сутки и не заметил смену типа цен. После выкладки исправления сбросим сохранённые цены, и K-004 увидит цену оптовой 2: 15,72».

## 5. K-005 покупает B-107 дороже, чем K-006

**Причина:** ожидания не совпадают с правилами — это не ошибка. У клиентов разные типы цен: K-005 — оптовая 1, K-006 — оптовая 2 (`data/clients.csv:6-7`). Цены B-107: 11.34 и 10.71 (`data/prices.csv:26-27`). Обоим одинаково применена акция «Октябрь» 4 % → 10.89 и 10.28.

**Как установлено:** `php run.php K-005 B-107` и `php run.php K-006 B-107`; тест «5».

**Что сделать сейчас:** ничего в системе. Если K-005 по объёму закупок или договору должен быть на оптовой 2 — это решение коммерческого отдела; после смены типа в 1С сбросить кеш клиента (см. №4).

**Ответ менеджеру:** «Это не ошибка: у K-006 тип цен "Оптовая 2", у K-005 — "Оптовая 1", поэтому цена разная. Если K-005 положена оптовая 2, это решает коммерческий отдел, после смены в 1С цена на сайте обновится».

## Как не допустить повторения

### Кеш (№4)

1. **Сброс при изменениях.** После обмена с 1С (цены, правила скидок) и при смене типа цен или персональной скидки клиента — удалять кеш затронутых клиентов/товаров. Самый простой вариант — сбрасывать весь кеш цен после каждого обмена.
2. **Ключ зависит от всего, что влияет на цену.** Добавить в ключ тип цен клиента и версию прайса/правил (например, дату последнего обмена): `price:{client}:{price_type}:{sku}:{qty}:{price_version}`. Тогда смена типа даёт новый ключ, старое значение просто не используется.
3. **Короткий TTL.** Сутки — слишком долго для цен, которые меняются в течение дня; 15–60 минут при сбросе по событию достаточно.
4. **Инструмент для поддержки.** Команда/кнопка «сбросить цены клиента» и показ в админке, из кеша ли цена и когда посчитана (`stored_at` уже есть в кеше).
5. **Порядок при исправлениях.** Сбрасывать кеш после выкладки исправления расчёта, а не до.

### Отсутствующая цена (№1)

1. **Не подставлять чужую цену.** Уже сделано: `basePrice()` бросает исключение. На витрине вместо цены показывать «цена по запросу» и не давать оформить заказ — это правка в месте вызова, не в `PriceResolver`.
2. **Проверка полноты прайса после обмена с 1С.** Отчёт «товар × тип цен без цены» (для каждого активного товара должна быть цена каждого типа, по которому есть клиенты). Сейчас такой отчёт показал бы `B-105 / DEALER`.
3. **Оповещение.** Если отчёт не пустой — письмо/сообщение ответственному за цены в 1С; ошибки `Нет цены …` с сайта — в лог и в мониторинг.
4. **Контроль на стороне 1С.** Не выгружать товар на сайт, пока у него не заполнены все типы цен (или выгружать с пометкой, что цены нет).
